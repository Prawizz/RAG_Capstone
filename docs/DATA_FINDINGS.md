## 2. ปัญหาภาษาไทยที่พบ แยกตามวิธีจัดการ

### 2.1 Normalize ได้ (กฎตายตัว ไม่ต้องเดา)

| ปัญหา | ตัวอย่างจริง | ถูกต้อง | พบใน |
|---|---|---|---|
| สระอำแยกร่าง | `ดําเนินธุรกิจ`, `จํากัด` | ดำเนินธุรกิจ, จำกัด | KBANK, PTT |
| สระ/วรรณยุกต์ซ้ำ | `มีีนาคม`, `วัันที่่`, `ปีี`, `เป็็น` | มีนาคม, วันที่, ปี, เป็น | PTT (ฟอนต์ Thongterm) |
| สระอำซ้ำ + อักขระแทนที่ | `จำำ�กััด`, `กำ�ไร`, `รู้้�` | จำกัด, กำไร, รู้ | PTT |
| อักขระควบคุมแทรกหลังวรรณยุกต์ | `ที่่\x1c`, `ตั้้\x02ง`, `ขึ้้\x86น` | ที่, ตั้ง, ขึ้น | PTT |
| zero-width / NBSP / ช่องว่างยาวในสารบัญ | `\xa0\xa0\xa0\xa036` | ตัดทิ้ง | ทุกไฟล์ |

เหตุผลที่ "สระ/วรรณยุกต์ซ้ำ" ถือเป็น normalize ได้: ภาษาไทยที่ถูกต้องไม่มีกรณีที่เครื่องหมายตัวเดียวกันอยู่ติดกันสองตัว การยุบให้เหลือตัวเดียวจึงไม่ต้องเดาความหมาย

### 2.2 Repair ได้บางส่วน (ขึ้นกับฟอนต์ และกำกวม)

KBANK ฟอนต์ตระกูล **DBThaiTextX** — glyph วรรณยุกต์แบบตำแหน่งเลื่อน ถูก map เป็นอักษรละติน

| ดึงได้ | ถูกต้อง | สังเกต |
|---|---|---|
| `เน่Çอหาประกาศ` | เนื้อหาประกาศ | `ื` → `่`, `้` → `Ç` |
| `การให้เชmาซ่Çอ` | การให้เช่าซื้อ | `่` → `m` |
| `พระราชกฤษฎ่กา` | พระราชกฤษฎีกา | `ี` → `่` |
| `ล่สซิÆง` | ลีสซิ่ง | `ี` → `่`, `่` → `Æ` |

อีก subset ของฟอนต์เดียวกันใส่เครื่องหมายเกินมาที่พยัญชนะบางตัว — `บริษัที่` (บริษัท), `ดูำรง` (ดำรง), `โดูย่` (โดย), `ที่่Æดู` (ที่ดู → ที่)

**ทำไมกำกวม:** `่` ตัวเดียวอาจมาจาก `ี`, `ื` หรือ `ู` ก็ได้ และ `ที่` ที่ดึงได้อาจเป็นคำว่า "ที่" จริง หรือเป็น `ท` ที่ถูกเติมเครื่องหมายเกินก็ได้ การแก้จึงต้อง (ก) ทำราย span โดยดูชื่อฟอนต์ เพราะความผิดเป็นของฟอนต์แต่ละตัว และ (ข) ใช้พจนานุกรมช่วยเลือก ซึ่งเข้าข่าย "เดา" — ต้องตั้งเกณฑ์สูง ถ้าไม่ถึงเกณฑ์ให้ส่งหน้านั้นไป OCR

### 2.3 ต้อง OCR

| กรณี | ตัวอย่าง |
|---|---|
| ข้อความขยะทั้ง span | KBANK `DBThaiTextX-Italic`: `\r\x03\x03\x84n®¢º¦\x8a³\x83...` |
| หน้าเป็นภาพทั้งหน้า | CPALL หน้า 386+ — ชั้นข้อความมีแค่หัวกระดาษ `รายงานทางการเงิน 394` เนื้อหาเป็นภาพตารางงบการเงิน |

งบการเงิน 155 หน้าของ CPALL คือกรณี OCR ที่ยากที่สุด: ตารางตัวเลขภาษาไทยหนาแน่น

### 2.4 ⚠️ แก้ความเข้าใจเดิม: ไม่มี ToUnicode ≠ ข้อความพัง

design เดือนกันยาเสนอว่า "ฟอนต์ไม่มี ToUnicode → ส่ง OCR ทันที" ข้อมูลจริงบอกว่า**กฎนี้ผิด**

- PTT ฟอนต์ `PTT45Pride` ไม่มี ToUnicode แต่ดึงได้ถูกต้อง: `ปตท. แข็งแรงร่วมกับสังคมไทย`
- KBANK ฟอนต์ `CordiaNew-Bold` ไม่มี ToUnicode แต่ดึงได้ถูกต้อง: `One Report`, `K‑Strategy`
- ในทางกลับกัน ฟอนต์ที่**มี** ToUnicode ก็ยังพังได้ (Thongterm ของ PTT ใส่เครื่องหมายซ้ำ)

**สรุป:** ด่านตรวจต้องตัดสินจาก**เนื้อข้อความที่ดึงได้** ไม่ใช่จากคุณสมบัติของฟอนต์

## 3. ด่านตรวจคุณภาพ — สัญญาณที่ใช้ได้จากข้อมูลจริง

| สัญญาณ | จับกรณีไหน |
|---|---|
| อักษรละติน-1 (`Ç Æ É Ê ®` ฯลฯ) อยู่ระหว่างอักษรไทย | DBThaiTextX |
| อักขระควบคุม C0/C1 และ U+FFFD | Thongterm, ข้อความขยะ |
| ลำดับเครื่องหมายที่เป็นไปไม่ได้ในภาษาไทย (เครื่องหมายซ้ำ, วรรณยุกต์ไม่มีฐาน) | Thongterm, DBThaiTextX |
| สัดส่วนคำที่อยู่ในพจนานุกรมหลังตัดคำ | ทุกกรณี (ใช้หลัง normalize) |
| ชั้นข้อความสั้นมาก + ภาพเต็มหน้า | หน้าสแกน CPALL |

ลำดับที่ถูกต้อง: **normalize ก่อน แล้วค่อยวัด** — ถ้าวัดก่อน PTT จะถูกส่ง OCR ทั้งไฟล์ ทั้งที่แก้ได้ด้วยกฎตายตัว

## 4. ข้อสังเกตเฉพาะ CPALL

ไฟล์นี้ไม่น่าใช่ไฟล์ต้นฉบับที่ยื่นตลาดหลักทรัพย์:
- มีข้อความ `#MARKER:TOC`, `#MARKER:PART_1`, `#MARKER:PART_3` อยู่ในชั้นข้อความ
- ทั้ง 546 หน้าใช้ฟอนต์แค่ TH Sarabun New กับ DejaVu Sans
- ไม่มีข้อมูลผู้ผลิตไฟล์

ดูเหมือนมีคนสร้างไฟล์นี้ใหม่จากต้นฉบับ ถ้าไม่ตั้งใจ marker จะหลุดเข้าไปใน chunk ถ้าตั้งใจ (ไว้แบ่งส่วนสำหรับ eval) ingestion ต้องดึงออกมาเป็น metadata แล้วลบจากข้อความ — **ต้องถามคนที่ทำไฟล์**

## 5. ปัญหาของ eval sets

| | rag_evaluation_100 | rag_evaluation_1000 |
|---|---|---|
| ประเภท | question 70 · unanswerable 20 · chitchat 10 | exact_match 400 · multi_hop 300 · unanswerable 200 · chitchat 100 |
| citation หาเจอในข้อความที่ PyMuPDF ดึงได้ | 57/70 | exact_match 327/400 · multi_hop 6/300 |

### 5.1 ครอบคลุมแค่ ~1% ของเอกสาร ⚠️

citation **ทั้งหมด**มาจากไม่กี่หน้าแรกของแต่ละไฟล์

| ไฟล์ | หน้าที่ถูกอ้างถึง | จำนวนหน้าที่ต่างกัน |
|---|---|---|
| CPALL | 1–7 | 4 |
| KBANK | 1–4 | 3 |
| PTT | 5–10 | 6 |

รวม **13 หน้าจาก 1,190** — ไม่มีคำถามเกี่ยวกับหน้าสแกนเลย ไม่มีคำถามจากตารางงบการเงิน ไม่มีคำถามจากเนื้อหาลึกในเอกสาร eval ชุดนี้จึงวัด OCR ไม่ได้ และบอกไม่ได้ว่า retrieval ทำงานได้ดีแค่ไหนบนเอกสาร 500 หน้า

### 5.2 Ground truth มีข้อความพังปนอยู่ ⚠️

citation ของ KBANK มาจากเครื่องมือดึงข้อความอีกตัวที่พังคนละแบบ:

```
ณ วันท่� 31 ธันวาคม 2568 ธนาคารม่ทุนจดทะเบ่ยน ... ม่ลค�าหุ้น
→ ควรเป็น: วันที่ ... ธนาคารมีทุนจดทะเบียน ... มูลค่าหุ้น
```

การวัดคุณภาพ extraction เทียบกับ ground truth ที่มาจาก extractor อีกตัวเป็นการวัดวน — ถ้าเราดึงได้**ดีกว่า** จะถูกนับว่าผิด

### 5.3 ซ้ำกันมาก

ข้อ answerable 700 ข้อมี citation ไม่ซ้ำกันแค่ **327 แบบ** — citation เดียวถูกใช้ซ้ำถึง 20 ข้อ ขนาดตัวอย่างจริงจึงน้อยกว่า 1,000 มาก

### 5.4 รูปแบบ multi_hop

citation ของ multi_hop รวมหลายท่อนด้วย `\n---\n` → harness ต้องแยกแล้วตรวจทีละท่อน (ตอนนี้จึงหาเจอแค่ 6/300)

### 5.5 ข้อเสนอสำหรับ eval ชุดใหม่

1. กระจายคำถามตามส่วนของเอกสาร — ต้นเล่ม, กลางเล่ม, ตาราง, หน้าสแกน
2. Ground truth มาจากการอ่านเอกสารจริงด้วยตา (หรือข้อความที่ normalize แล้วผ่านการตรวจโดยคน) ไม่ใช่ output ของ extractor ตัวใดตัวหนึ่ง
3. ตัดข้อที่ซ้ำ citation กันออก
4. ระบุหน้าที่มาของ citation ไว้ในข้อมูลเลย จะได้วัด citation ระดับหน้าได้

## 6. ความหมายต่อแผน ingestion-first

- **สามไฟล์นี้แทน proxy pack ได้** — มีปัญหาจริงเกือบทุกแบบที่ออกแบบไว้ ยกเว้นภาพสแกนที่รู้คำตอบ
- **CER ยังต้องใช้หน้าสแกนสังเคราะห์จาก corpus** เพราะงบการเงิน CPALL ไม่มี ground truth
- **ได้คู่ทดสอบ Thai normalization จากของจริงทันที** — ตัวอย่างในข้อ 2.1 ขุดแบบอัตโนมัติได้อีกหลายพันคู่
- **ได้สเปกด่านตรวจคุณภาพจากของจริง** (ข้อ 3)
- **ลำดับงานที่ข้อมูลบอก:** normalizer v1 ต้องมาก่อน OCR เพราะถ้าไม่ normalize ก่อน PTT จะถูกตีว่าพังทั้งไฟล์
