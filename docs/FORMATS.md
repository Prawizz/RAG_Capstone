## 0. หลักร่วมของทุกประเภท

ทุกประเภทไหลเข้า contract เดียวกัน:

```
ไฟล์ → ตรวจชนิดจาก magic bytes → extractor ของประเภทนั้น
     → Document → Unit (หน้า / สไลด์ / ส่วน / ช่วงเซลล์) → Block
     → normalize → ด่านตรวจคุณภาพ → สถานะราย unit
```

**Unit** คือหน่วยที่ใช้อ้างอิงใน citation ใช้นับสถานะ และใช้เป็น key ของ cache ทุกประเภทต้องมี `position` (ตำแหน่งที่เครื่องอ่านได้) และ `label` (ข้อความที่แสดงให้ user เห็น เช่น "หน้า 47" หรือ "สไลด์ 12")

### การตรวจชนิดไฟล์

| Magic bytes | เป็นอะไร | แยกต่อด้วย |
|---|---|---|
| `%PDF` | PDF | — |
| `PK\x03\x04` (ZIP) | docx / pptx / xlsx | เปิดดูข้างใน: `word/`, `ppt/`, `xl/` |
| `D0 CF 11 E0` (OLE2) | doc / ppt / xls รุ่นเก่า | ชื่อ stream: `WordDocument`, `PowerPoint Document`, `Workbook` |
| อย่างอื่น | ไม่รองรับ | ปฏิเสธพร้อมแจ้งรายการประเภทที่รองรับ |

## 1. ⚠️ คำถามที่ต้องตกลงก่อน: "หน้า" ของแต่ละประเภทคืออะไร

ข้อนี้กระทบ KPI สามตัว คือ citation accuracy, page ingest และโควตา 350 หน้า

| ประเภท | มีหน้าจริงไหม | Unit ที่เสนอ | นับโควตาอย่างไร |
|---|---|---|---|
| PDF | มี | หน้า | 1 หน้า = 1 |
| PPTX | มี (สไลด์) | สไลด์ | 1 สไลด์ = 1 |
| **DOCX** | **ไม่มี** — Word จัดหน้าตอนแสดงผล ในไฟล์ไม่ได้เก็บไว้ | หัวข้อ + ช่วงย่อหน้า | ต้องตกลง (ดูข้างล่าง) |
| XLSX | ไม่มี | ชื่อชีต + ช่วงเซลล์ของตาราง | ต้องตกลง (เป็นคำถามค้างอยู่แล้ว) |

**DOCX เป็นปัญหาที่ยังไม่มีใครพูดถึง** ผู้ใช้คาดหวังว่า citation จะบอก "หน้า 12" แต่ docx ไม่มีเลขหน้า มีสองทาง:

| ทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| ก. อ้างด้วยหัวข้อ เช่น "หมวด 3 > การลา" | แม่นยำ ไม่ขึ้นกับการจัดหน้า (docstring ใน repo เสนอทางนี้ไว้แล้ว) | ไม่มีเลขหน้าให้ดู |
| ข. แปลงเป็น PDF ด้วย LibreOffice แล้วใช้เลขหน้า | มีเลขหน้า | การจัดหน้าของ LibreOffice ไม่ตรงกับ Word เลขหน้าอาจคลาดกับที่ user เปิดเห็น |

**ข้อเสนอ:** ใช้ทาง ก เป็นหลัก แล้วนับโควตาด้วยจำนวนหน้าที่ LibreOffice แปลงได้ (ใช้นับอย่างเดียว ไม่ใช้อ้างอิง) — ต้องเอาไปตกลงกับบริษัทคู่กับเรื่อง Excel

## 2. PDF ที่มีชั้นข้อความ

| | |
|---|---|
| Unit | หน้า |
| เครื่องมือ | PyMuPDF `get_text("dict")` — ได้ span พร้อมขนาดฟอนต์และตัวหนา ใช้อนุมานหัวข้อ; ถ้ามีสารบัญฝังในไฟล์ใช้แทนได้เลย (KBANK มี) |
| ไฟล์ทดสอบ | One Report 3 ฉบับ + `mock_corpus.pdf` |

**ปัญหาที่ต้องรับมือ** (จากข้อมูลจริง)
- ปัญหาภาษาไทยทั้งหมดใน DATA_FINDINGS ข้อ 2 — normalize ก่อน แล้วด่านตรวจตีตกส่วนที่แก้ไม่ได้ไปเป็น `needs_ocr`
- ลำดับการอ่านหลายคอลัมน์ — PTT มี text block เฉลี่ย 51 ก้อนต่อหน้า
- หัวกระดาษ/ท้ายกระดาษซ้ำทุกหน้า — ต้องดูข้ามหน้าถึงจะตัดได้
- ตาราง — ดึงแบบธรรมดาแล้วโครงสร้างหายหมด
- CPALL มี `#MARKER:` อยู่ในชั้นข้อความ

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ (v2) |
|---|---|
| ข้อความรายหน้า + block + ขนาดฟอนต์, normalize, ด่านตรวจ, สถานะรายหน้า | ลำดับการอ่าน (XY-cut หรือ Docling สำหรับหน้าซับซ้อน), อนุมานหัวข้อ, ตัดหัว/ท้ายกระดาษ, ตาราง |

## 3. PDF ที่เป็นภาพสแกน

| | |
|---|---|
| Unit | หน้า |
| การตรวจ | ตัดสิน**รายหน้า** — ชั้นข้อความสั้นมาก + ภาพครอบเกือบเต็มหน้า |
| ขั้นตอน | render หน้าเป็นภาพ (200–300 dpi) → OCR → normalize → ด่านตรวจ |
| เครื่องมือ | ตัวเลือก: Tesseract (tha+eng), PaddleOCR, Typhoon OCR — เลือกจาก CER |
| ไฟล์ทดสอบ | CPALL หน้า 386+ (155 หน้า ไม่มีคำตอบ), หน้าสแกนสังเคราะห์จาก corpus (รู้คำตอบ) |

**ปัญหาที่ต้องรับมือ**
- งบการเงินของ CPALL เป็นตารางตัวเลขหนาแน่น — กรณีที่ยากที่สุด
- ช้า — ต้องมีเพดานเวลาต่อหน้า
- ความละเอียดภาพมีผลต่อ CER มาก — ต้องจูน

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ (v2) |
|---|---|
| ตรวจรายหน้าได้ + ต่อ Tesseract ไว้ก่อนให้เส้นทางทำงาน | เทียบ engine แล้วเลือก, จูน dpi, รองรับตาราง |

## 4. DOCX

| | |
|---|---|
| Unit | หัวข้อ + ช่วงย่อหน้า (ดูข้อ 1) |
| เครื่องมือ | python-docx — ได้ย่อหน้าพร้อมชื่อ style (`Heading 1/2/3` → ระดับหัวข้อ) และตาราง |
| ไฟล์ทดสอบ | `mock_corpus.docx` — ต้องหาไฟล์จริงเพิ่ม |

**ข่าวดี:** ข้อความไทยใน docx เก็บเป็น Unicode อยู่แล้ว ปัญหาฟอนต์แบบ PDF แทบไม่มี

**ปัญหาที่ต้องรับมือ**
- **หัวข้อปลอม** — คนจำนวนมากทำหัวข้อด้วยการกดตัวหนาเอง ไม่ใช้ style จึงไม่มี `Heading` ให้อ่าน ต้องเดาจากขนาดฟอนต์แบบเดียวกับ PDF
- **ข้อความในกล่องข้อความ (text box)** — python-docx มองไม่เห็น ต้องอ่าน XML ตรง
- **หัวกระดาษ ท้ายกระดาษ เชิงอรรถ** — แยกเก็บ ไม่ปนกับเนื้อหา
- **Track changes** — ต้องตัดสินใจว่าเอาข้อความฉบับไหน (เสนอ: ฉบับที่ยอมรับการแก้ไขแล้ว)
- **ตารางที่มีเซลล์ผสาน**
- **ภาพที่ฝังในเอกสาร** — ภาพเดี่ยวอยู่นอก scope อยู่แล้ว เสนอให้ข้ามแล้วบันทึกว่ามีภาพที่ไม่ได้อ่าน

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ (v4) |
|---|---|
| ย่อหน้า + หัวข้อจาก style + ตาราง | หัวข้อปลอม, text box, หัว/ท้ายกระดาษ, track changes |

## 5. PPTX

| | |
|---|---|
| Unit | สไลด์ |
| เครื่องมือ | python-pptx — ไล่ shape ในแต่ละสไลด์: ช่องหัวเรื่อง, กล่องข้อความ, ตาราง, กลุ่ม shape (ต้องไล่ลึกแบบ recursive), บันทึกผู้บรรยาย |
| ไฟล์ทดสอบ | **ยังไม่มี** — สร้างจาก corpus + หาไฟล์จริง |

**ปัญหาที่ต้องรับมือ**
- **ลำดับการอ่าน shape** — ในไฟล์ไม่ได้เรียงตามที่ตาเห็น ต้องเรียงตามตำแหน่งบนลงล่าง ซ้ายไปขวา
- **SmartArt** — python-pptx อ่านไม่ได้ ต้องอ่าน XML
- **กราฟ** — มีแต่ข้อมูลตัวเลข เก็บแค่ชื่อกราฟกับชื่อแกน
- **สไลด์ที่เป็นภาพทั้งแผ่น** — ข้อความอยู่ในภาพ ต้องตัดสินใจว่าจะ OCR หรือไม่ (เสนอ: ติด `needs_ocr` เหมือน PDF)
- **สไลด์ซ่อน** — เสนอให้ข้ามและบันทึกไว้
- **ข้อความต่อสไลด์น้อยมาก** — บันทึกผู้บรรยายสำคัญกว่าที่คิด เพราะมักเป็นที่เดียวที่มีประโยคเต็ม

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ (v4) |
|---|---|
| หัวเรื่อง + กล่องข้อความ + ตาราง + บันทึกผู้บรรยาย เรียงตามตำแหน่ง | กลุ่ม shape ซ้อน, SmartArt, กราฟ, สไลด์ภาพ |

## 6. XLSX

| | |
|---|---|
| Unit | ชื่อชีต + ช่วงเซลล์ของตาราง |
| เครื่องมือ | openpyxl แบบ `data_only=True` (สูตรอยู่นอก scope เอาแค่ค่าที่คำนวณแล้ว) |
| ไฟล์ทดสอบ | **ยังไม่มี** — สร้างสมุดเบอร์ต่อ ตารางราคา (ใน eval set มีคำถามเรื่องเบอร์ต่อเยอะ) + หาไฟล์จริง |

รายละเอียดเต็มอยู่ใน proposal เดือนกันยา ข้อ 4.3 สรุปสั้นๆ:

1. **ตรวจหาขอบเขตตาราง** — หนึ่งชีตมีหลายตารางได้
2. **ใช้สัญญาณที่ผู้ทำไฟล์ใส่ไว้ก่อนเดา** — Table object, AutoFilter, freeze panes
3. **แยกประเภท** — เอกสารในรูปตาราง / ตารางอ้างอิงเล็ก / ตารางข้อมูลใหญ่ / รายงานซับซ้อน
4. **ค่าที่แสดงผล ไม่ใช่ค่าดิบ** — `0.18` ต้องเป็น `18%`, เลขศูนย์นำหน้าต้องไม่หาย
5. **เขียนแถวแบบชื่อคอลัมน์กำกับทุกค่า** — `แผนก: HR | เบอร์ต่อ: 2999`

**กรณีเฉพาะ:** ไฟล์ที่ไม่ได้บันทึกจาก Excel อาจไม่มีค่าที่คำนวณไว้ล่วงหน้า ทำให้อ่านได้เป็นค่าว่างทั้งคอลัมน์โดยไม่มี error — ต้องจับกรณีนี้ให้ได้

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ (v4) |
|---|---|
| ตรวจขอบเขต + สัญญาณจากผู้ทำไฟล์ + format ตัวเลข; รองรับเอกสารและตารางเล็ก; **ตารางใหญ่ปฏิเสธพร้อมเหตุผล** | หัวตารางหลายชั้น, รายงานซับซ้อน, ตารางใหญ่แบบสองชั้น (คำอธิบายเข้า index ข้อมูลเข้าฐานข้อมูล) |

## 7. DOC / PPT / XLS รุ่นเก่า

| | |
|---|---|
| ขั้นตอน | แปลงด้วย LibreOffice แบบไม่มีหน้าจอ → docx / pptx / xlsx → extractor ตัวเดียวกับข้างบน |
| เก็บ | ไฟล์ต้นฉบับเสมอ + `converted_from` |
| ไฟล์ทดสอบ | **ยังไม่มี** — แปลงไฟล์ทดสอบข้างบนย้อนกลับเป็นรุ่นเก่า + หาไฟล์จริงที่เก่าจริง |

**ปัญหาที่ต้องรับมือ**
- **LibreOffice ค้างได้** — ต้องมีเพดานเวลาแล้ว kill process
- **รันพร้อมกันหลายตัวแล้วชนกัน** — LibreOffice ล็อก profile ของผู้ใช้ ต้องแยก profile ต่อ process
- **ไฟล์ Word รุ่นเก่ามากๆ** (ก่อน Word 97) แปลงไม่ได้ — ปฏิเสธพร้อมเหตุผล
- **ไฟล์มีรหัสผ่าน** — ปฏิเสธพร้อมเหตุผล
- **ภาษาไทยในไฟล์เก่า** อาจเข้ารหัสแบบ Windows-874 — LibreOffice จัดการได้เกือบหมด แต่ต้องเทสต์
- **Docker image** ต้องมี LibreOffice + ฟอนต์ไทย (`fonts-thai-tlwg`) — image ใหญ่ขึ้นราว 500 MB

| ระดับพื้นฐาน (v1) | ระดับสมบูรณ์ |
|---|---|
| แปลงได้ + เพดานเวลา + แยก profile | ตามความสมบูรณ์ของ extractor ปลายทาง |
