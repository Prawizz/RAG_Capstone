## 0. สรุป

1. ทำ **ingestion ให้เกือบสมบูรณ์ก่อน** เพราะเป็นเพดานคุณภาพของทั้งระบบ และมี KPI ของตัวเองวัดได้โดยไม่ต้องรอ retrieval — KPI ≥90% ห้าในเจ็ดตัวเป็นของ ingestion ล้วน
2. ลำดับสร้าง: contract (เสร็จแล้ว) → PDF extractor → normalizer v1 → ด่านตรวจคุณภาพ → format อื่น — ทำ PDF ให้สุดทางก่อนเพราะเป็นความเสี่ยงสูงสุด
3. Ingest v1 รองรับ**ครบทุกประเภทในระดับพื้นฐาน**ผ่าน contract เดียว เพื่อพิสูจน์ว่า contract รองรับทุกประเภทก่อน freeze แล้วค่อยลงลึก PDF/OCR, repair และ Office ใน v2–v4
4. **ตอนระบบทำงาน normalizer ต้องมาก่อนด่านตรวจและ OCR** — ถ้าไม่ normalize ก่อนวัด PTT จะถูกส่งไป OCR ทั้งไฟล์ ทั้งที่แก้ได้ด้วยกฎตายตัว (แต่ตอน**สร้าง** ทำ extractor ก่อนได้ เพื่อให้ขุดตัวอย่างจาก output จริง)
5. **Eval set ปัจจุบันวัด retrieval ได้ไม่ครอบคลุม** — 1,000 ข้อมาจากแค่ 13 หน้า และ ground truth บางส่วนมีข้อความพังปนอยู่ ต้องเริ่มสร้างชุดใหม่คู่ขนานไปเลย
6. **Stretch goals ที่ทำให้ standout** — auto routing ที่เสนอกล่องจากหลักฐานการค้นจริงและไม่เดาเมื่อไม่มั่นใจ พร้อมตัวเลขเทียบกับวิธีอื่น และ demo console ขั้นต่ำไว้เดโมกับ debug ทั้งสองอย่างทำหลัง KPI หลักเดินตามแผน

## 3. หลักการ

1. **ทุกเวอร์ชันมีเกณฑ์ผ่านที่วัดได้** — ไม่ผ่านไม่ไปต่อ
2. **วัดก่อนเขียน** — harness มาก่อน extractor
3. **Contract ก่อน แล้วค่อยแยกกันทำ** — `models.py` freeze ก่อนเขียน extractor
4. **ตัวเลขจาก mock ไม่ใช่ KPI** — mock ใช้ตรวจ logic, KPI วัดบนไฟล์จริง
5. **ทุกอย่างที่พึ่งทีมอื่นต้องมี mock และวัน trigger**
6. **Task จะ "เสร็จ" เมื่อ** — โค้ด + unit test ผ่าน, eval ไม่ตกจากรอบก่อน (ถ้าตกต้องมีเหตุผลบันทึกไว้), และถ้าแตะ contract ต้องอัปเดตเอกสารใน commit เดียวกัน

### 4.2 Ingest v1 — ครบทุกประเภทในระดับพื้นฐาน

**ขอบเขต:** ทุกประเภทใน scope ผ่าน contract เดียวกัน ในระดับพื้นฐาน — รายละเอียดต่อประเภทอยู่ใน `docs/FORMATS.md`

```
ตรวจชนิดจาก magic bytes → extractor ของประเภทนั้น → Unit + Block
→ normalize → ด่านตรวจคุณภาพ → สถานะราย unit → CLI
```

| ประเภท | ระดับพื้นฐานใน v1 |
|---|---|
| PDF ข้อความ | ข้อความรายหน้า + block + ขนาดฟอนต์ |
| PDF สแกน | ตรวจรายหน้าได้ + ต่อ Tesseract ไว้ให้เส้นทางทำงาน (ยังไม่เลือก engine) |
| DOCX | ย่อหน้า + หัวข้อจาก style + ตาราง |
| PPTX | หัวเรื่อง + กล่องข้อความ + ตาราง + บันทึกผู้บรรยาย เรียงตามตำแหน่ง |
| XLSX | ขอบเขตตาราง + สัญญาณจากผู้ทำไฟล์ + format ตัวเลข; ตารางใหญ่ปฏิเสธพร้อมเหตุผล |
| DOC/PPT/XLS | แปลงผ่าน LibreOffice + เพดานเวลา + แยก profile |

ทุก unit ได้สถานะ `ok` / `needs_ocr` / `failed` / `rejected` พร้อมเหตุผล

**ลำดับภายใน v1:** contract ✅ → ตัวตรวจชนิด + PDF ข้อความ (T02) → normalizer (T03) → ด่านตรวจ (T04) → DOCX → PPTX → XLSX → legacy (ต้องรอสามตัวก่อนหน้า) → เส้นทางสแกน

P4–P5 ย้ายมาอยู่ใน T03 เพราะ normalizer ควรถูกทดสอบกับข้อความที่ extractor จริงดึงออกมา

**ทำไมครบทุกประเภทก่อน:** contract จะ freeze ได้อย่างมั่นใจก็ต่อเมื่อดันทุกประเภทผ่านมันแล้ว ถ้าทำ PDF อย่างเดียวก่อน มีโอกาสสูงที่ contract จะไม่รองรับสไลด์หรือช่วงเซลล์ แล้วต้องรื้อทีหลัง และ KPI "ingest ≥14/15 ไฟล์" ตกทันทีถ้าประเภทไหนยังไม่รองรับ

**ยังไม่ทำ:** เลือก OCR engine, repair ฟอนต์ DBThaiTextX (ติด `needs_ocr` ไว้ก่อน), ลำดับการอ่านแบบซับซ้อน, ตาราง PDF, cache, API

**เกณฑ์ผ่าน**
- ไฟล์ทดสอบทุกประเภท ingest ได้โดยไม่มีไฟล์ไหนพังทั้งไฟล์
- mock corpus (PDF และ DOCX) ถูกต้อง ≥99%
- หน้าสแกน 155 หน้าของ CPALL ได้ `needs_ocr` ครบ
- PTT ส่วนใหญ่ได้ `ok` หลัง normalize
- span ขยะของ KBANK ถูกจับได้
- ไฟล์รุ่นเก่าแปลงแล้วได้ผลเดียวกับไฟล์รุ่นใหม่ที่เนื้อหาเหมือนกัน
- รู้เวลาที่ใช้ต่อ unit ของแต่ละประเภท
- **Probe** — chunk + embed + ค้นแบบง่ายบน output ได้ (ครึ่งวัน แค่เช็คว่าขั้นถัดไปใช้ได้)

### 4.3 หลัง v1 — ลงลึก

## 6. Stretch goals — ส่วนที่ทำให้ standout

ทั้งสองอย่างนี้อยู่นอก scope เดิม จึงทำ**หลัง** KPI หลักเดินตามแผนเท่านั้น และถ้าเวลาไม่พอ ต้องตัดก่อนงาน core (ดูข้อ 11)

### 6.1 Auto routing แบบไม่เดา

**ปัญหาที่แก้:** ตอนนี้ user ต้องรู้เองว่าคำตอบอยู่กล่องไหน ถ้าเลือกผิดก็หาไม่เจอ

**หลักคิด:** ใช้หลักฐานจากการค้นจริงเป็นตัวตัดสิน ไม่ให้ LLM เดา และ**ระบบเสนอ แต่ user เป็นคนเลือก** จึงไม่ขัดกับ decision "ผู้ใช้เลือก source เอง"

```
คำถาม
  ↓ ① หากล่องที่ user เป็นสมาชิก (ACL มาก่อนทุกอย่าง)
  ↓ ② ค้นครั้งเดียวข้ามทุกกล่องนั้น ~50 chunk (กรองสิทธิ์ไฟล์ครบทุกชั้น)
  ↓ ③ รวมคะแนนเป็นรายกล่อง
  ↓ ④ ชนะขาด → เสนอ 1 กล่อง + ความมั่นใจ + หลักฐาน
     สูสี     → เสนอ 2 อันดับ
     ต่ำหมด   → "ไม่พบกล่องที่เกี่ยวข้อง"
  ↓ ⑤ user ยืนยัน → retrieve ปกติในกล่องเดียว
```

**ทำไมไม่หลอน:** กล่องที่เสนอมาจาก chunk ที่ค้นเจอจริง จึงเสนอกล่องที่ไม่มีอยู่หรือกล่องที่ user ไม่มีสิทธิ์ไม่ได้โดยโครงสร้าง อย่างแย่ที่สุดคือเสนอผิด ซึ่งวัดได้

**ทำไมไม่ชน KPI:** retrieve รอบจริงทำในกล่องเดียวเสมอ จึงไม่ปน source

**จุดเสียบเข้า contract:** `/retrieve` ที่ไม่มี `selected_source` เดิมคืน `SOURCE_REQUIRED` → เปลี่ยนเป็น `SOURCE_SUGGESTED` พร้อมกล่องที่เสนอ ความมั่นใจ และหลักฐาน Gateway ที่ไม่ใช้ฟีเจอร์นี้ยังทำงานได้เหมือนเดิม

**ข้อควรระวังทางเทคนิค**
- **กล่องใหญ่ได้เปรียบ** — ถ้านับจำนวน chunk ที่ติดอันดับ กล่องใหญ่จะชนะเสมอ ต้องใช้คะแนนที่ไม่เอนตามขนาด เช่นคะแนนสูงสุดหรือค่าเฉลี่ย top-3 ต่อกล่อง
- **Public/Private อยู่คนละ collection** — ค้นทั้งสองแล้วรวมผลได้เพราะใช้ embedding model ตัวเดียว ถ้ากล่องที่เสนอเป็น private ต้องติด Private flag ด้วย

**ตัวเทียบ** — ส่วนที่ทำให้ standout คือตัวเลขเทียบกับวิธีที่คนอื่นใช้

| วิธี | จุดอ่อนที่คาดว่าจะเห็น |
|---|---|
| LLM router (อ่านชื่อ/คำอธิบายกล่องแล้วเลือก) | เลือกแบบมั่นใจแม้ผิด, อาจตอบชื่อกล่องที่ไม่มีอยู่ |
| Description embedding | ขึ้นกับคุณภาพคำอธิบายที่ admin เขียน |
| ของเรา (หลักฐาน + ไม่เดา) | ต้องพิสูจน์ด้วยตัวเลข |

ตัวชี้วัด: ความแม่นยำเทียบกับอัตราที่ยอม route, จำนวนครั้งที่เสนอกล่องที่ไม่มีอยู่, จำนวนครั้งที่รั่วสิทธิ์ (ต้องเป็นศูนย์), ความถูกต้องของการไม่ route คำถามที่ไม่มีคำตอบ

**Benchmark ต้องยากพอ** — One Report 3 กล่องง่ายเกินไปเพราะคำถามมีชื่อบริษัทอยู่แล้ว ต้องมีกล่องที่เนื้อหาซ้อนกัน (เช่น HR กับ Finance ที่ต่างพูดเรื่องการเบิกค่าใช้จ่าย) และคำถามที่ไม่บอกว่ามาจากกล่องไหน

| # | งาน | ทำได้เมื่อไหร่ | Pts |
|---|---|---|---|
| R0 | Benchmark — กล่องเนื้อหาซ้อนกัน + คำถามติดป้ายกล่องที่ถูก + คำถามที่ไม่ควร route | **ตอนนี้** (คู่ขนาน สาย D) | 3 |
| R1 | ตัวเทียบ — LLM router, description embedding | หลังมี retrieval | 2 |
| R2 | รวมคะแนนรายกล่องจากหลักฐาน | หลังมี retrieval | 2 |
| R3 | Calibrate threshold + เสนอ top-2 + ไม่เดาเมื่อไม่มั่นใจ | หลัง R2 | 2 |
| R4 | เสียบเข้า contract + test ว่าไม่เสนอกล่องที่ไม่มีสิทธิ์ | หลัง ACL suite ผ่าน 100% | 1 |
| R5 | รายงานเปรียบเทียบทุกวิธี | ท้ายสุด | 1 |

**เงื่อนไข:** ต้องได้ไฟเขียวจากบริษัท (auto source routing อยู่ใน out of scope) และวางเป็น stretch goal ใช้ตอบคำถามอาจารย์เรื่อง technical contribution

## 8. Design decisions

| เรื่อง | ข้อเสนอ | สถานะ |
|---|---|---|
| ด่านตรวจคุณภาพ | ตัดสินจาก**เนื้อข้อความ**หลัง normalize ไม่ใช่จากคุณสมบัติฟอนต์ | แก้จาก design ก.ย. (กฎ "ไม่มี ToUnicode → OCR" ผิด ดู DATA_FINDINGS 2.4) |
| Normalize vs repair | normalize = กฎตายตัวไม่ต้องเดา, repair = เดาแบบมีหลักฐาน ต้องผ่านเกณฑ์สูง ไม่ถึง → OCR | ยืนยันแล้ว |
| Chunk ข้ามหน้า | ไม่ข้าม แต่แปะ section path ข้ามหน้า และขยายเพื่อนบ้านข้ามหน้าได้ตอน retrieve | เสนอ |
| ACL | 2 ด่าน — pre-filter ใน Qdrant + re-check กับ ACL store | รออาจารย์ |
| Public/Private | แยก Qdrant collection; private ผูกกับ box ตอนสร้าง | เสนอ |
| Service auth | อยู่ใน contract — mTLS หรือ signed token อายุสั้น | ต้องตกลงกับบริษัท |
| Chitchat / unanswerable | RAG คืน `no_relevant_context` + คะแนนสูงสุด ให้ Gateway ตัดสิน | เสนอ |
| KPI inline citation | แยกเป็นของเรา (ส่ง citation ครบ) กับของ Gateway (แสดงใน response) | รออาจารย์ |
| CPALL `#MARKER:` | ลบจากข้อความ หรือดึงเป็น metadata | รอคำตอบจากคนทำไฟล์ |

## 12. ทบทวนแผนนี้

**เปลี่ยนจาก v1**
- จาก walking skeleton เป็น ingestion-first — ข้อโต้แย้งหลักของ skeleton คือ "ไม่ไหลครบก็วัดไม่ได้" แต่ ingestion มี KPI ของตัวเองวัดได้อิสระ
- จาก "ใช้ PDF สาธารณะเป็น proxy pack" เป็นใช้ One Report 3 ฉบับที่ทีมหามา ซึ่งมีปัญหาจริงครบกว่า
- จาก "ขุดคู่ normalization อัตโนมัติ" เป็น "หาตัวอย่างอัตโนมัติ แต่คนตรวจคำตอบ" เพื่อไม่ให้วัดวน
- จาก "ไม่มี ToUnicode → OCR" เป็นตัดสินจากเนื้อข้อความ

**จุดอ่อนที่ยังเหลือ**
- Sprint mapping และจำนวน points ยังไม่ได้ทำใหม่ให้ตรงลำดับ ingestion-first — ต้องทำหลังทีมเห็นด้วยกับลำดับนี้
- ยังไม่มี velocity
- หน้าสแกนของ CPALL (งบการเงิน) ไม่มี ground truth — วัด OCR บนตารางตัวเลขจริงไม่ได้ จนกว่าจะหามาได้
- ถ้า ingestion ลากเกินปลาย S2 งาน ACL ที่เป็น KPI 100% จะเสี่ยงทันที
